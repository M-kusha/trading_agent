01Executive verdict

This system cannot currently learn. Its agent has been training on a constant zero vector, and the failure is silent by construction. Underneath that blocker the engineering is better than its reputation — the data has no look-ahead, the fill ordering is causal, a real chronological holdout exists — but the project is carrying roughly three times the code it can validate, maintains two divergent implementations of nearly every decision-critical concept, and evaluates itself on a period whose buy-and-hold return is +32.8%.

The recommendation is repair-then-reduce-scope, not rewrite and not continue. The causal core (environment, execution model, feature data) is worth keeping and is hard to reproduce. Everything above it needs to be re-derived from evidence rather than accumulated. Critically, I do not recommend deleting the disconnected subsystems: several of them (seasonality, the neural world model, the memory loss-risk head) are the only implementations of genuinely orthogonal ideas in the repository. They should be gated behind ablations, not removed on reachability grounds.

On the previous audit's 10–15% estimate for eventual live profitability: I find it roughly right for the wrong reasons. That number was driven by code defects, which are all repairable. The durable constraint is different and worse — the information budget. XAUUSD M15 over 2021–2025 yields on the order of 3,223 effectively independent samples and 1,091 trading days, against a policy input of 106 dimensions. That ratio, not the bug count, is what caps this design. My assessment is in §16, and it separates software correctness from edge existence deliberately, because fixing the former does not create the latter.

The single most consequential finding

It is not the zero-observation bug. It is that training and live execution build their inputs from entirely different code: different expert implementations, different world models, a seasonality expert that is real in live and a hardcoded constant in training. Even a perfectly trained policy would meet unfamiliar inputs on its first live tick.

And that split has an identifiable cause, not a careless one. The modules/ subsystems are built as real-time services — 401 datetime.now(), 610 time.time(), 36 time.sleep, 178 threading references — so they cannot run inside a fast simulation loop. Session logic believes the market is closed when you train at night; cooldowns keyed to wall-clock never expire. Writing simplified, time-pure versions inside envs/prop_firm/ was the correct response to a genuine blocker. See F0 in §5. The fix — modules/utils/simulation_time.py, 658 LOC — was already written on the archived rl-driven-trading branch and never reached this one.

Two pieces of good news from the data investigation

The data is genuinely FTMO. Verified read-only against the installed FTMO terminal: 400 overlapping M15 bars per symbol match 100.00% exactly on open, high, low, close and spread. metadata.json is accurate. (config/live.yaml, however, points at MetaQuotes-Demo through a terminal path that does not exist — that needs fixing.)

The 7.5 months of missing data is the regime holdout this project needs. 14,451 new XAUUSD M15 bars covering Dec 2025 – Jul 2026: −5.5% net against the training sample's +149.8%, at 2.25× volatility and 5.1× spread. It should be reserved as the untouched final test set, not merged into training.

02What the current system actually does

Stated intent: a PPO agent with curriculum learning, an expert voting committee, a world model, a learned memory, and prop-firm risk governance, trading XAUUSD on M15.

Actual behaviour, verified by execution:

  1. train/train_prop_firm.py loads four timeframes of precomputed CSV features and builds PropFirmTradingEnv.
  2. The env attempts to import modules.meta.ppo_observation_builder. The import raises. A try/except Exception at envs/prop_firm_env.py:100 swallows it, sets PPO_OBS_SIZE = 90 and OBS_BUILDER_AVAILABLE = False.
  3. _get_observation() therefore dispatches to _fallback_observation(), whose entire body is return np.zeros(90, dtype=np.float32).
  4. PPO trains against a constant input. Loss decreases as the policy collapses to a fixed action distribution. One logger.warning is the only signal.

Runtime verified — reproduced on a real 8-episode run; the log line [OBS] PPOObservationBuilder not available -> fallback observation appears and every observation is identically zero.

Meanwhile the 39 modules in config/module_registry.yaml — the experts, committee, world model, risk controllers, memory — are loaded only by the live orchestrator. They have no influence on training whatsoever.

05Critical hidden failures

F0 — ROOT CAUSE: the modules/ subsystems are real-time services, not simulation components

This is the finding that explains every duplication in this report. It was raised from operator memory — "the modules were acting like they were in real time, so I had to synthesize things" — and it is fully confirmed.

Statically verified Wall-clock and concurrency coupling, modules/ versus the training path:

pattern          modules/              envs/ (training)
datetime.now     401 in 57 files       4 in 4 files
time.time()      610 in 85 files       4 in 2 files
time.sleep        36 in 24 files       0
asyncio          184 in 25 files       0
threading        178 in 44 files       0
Thread(           34 in 25 files       0

Concretely, these break under simulation:

  • SmartInfoBusConfig.max_data_age_seconds = 600 and DataVersion.age_seconds() = time.time() - self.timestamp — pure wall clock. In a loop running thousands of bars per second, everything is either permanently fresh or permanently stale, never correct.
  • Background daemon threads sleep on wall clock inside components that must be step-synchronous: modules/memory/unified_memory.py:449, modules/meta/ppo_agent_shell.py:383, modules/monitoring/health_monitor.py:1436, modules/position/position_base.py:439 (sleep(30)), modules/core/module_system.py:1221 (sleep(5)).
  • Session, cooldown and seasonality logic reads datetime.now(), so training at 02:00 local time makes every module believe the market is closed — regardless of the bar's actual timestamp.
  • 18+ modules use datetime.now() for decisions, led by strategy_introspector (26), execution_quality_monitor (24), dynamic_risk_controller (21), models/world_model (21).

The workaround — reimplementing simplified, time-pure versions inside envs/prop_firm/ — was a rational engineering response to a real blocker. It is the direct cause of the train/serve skew in F-series findings below. The mistake was not the workaround; it was that the workaround became permanent and undocumented.

The fix already exists and is not on this branch. modules/utils/simulation_time.py (658 LOC) lives on the archived archive/rl-driven-trading tag. Its own docstring names these exact symptoms: "Training at night = all signals see 'market closed'"; "Cooldowns based on wall-clock = never expire during fast simulation". It provides set_simulation_mode(), get_simulation_time(), get_session_info(), publish_simulation_time(), and a StepCooldownTracker that replaces wall-clock cooldowns with step counts. Runtime verified — recovered and read from the tag.

This reframes the central recommendation. The right move is not "pick the smaller expert implementation". It is: inject the simulation clock, make the real modules runnable in training, and only then decide by ablation which implementation survives.

F1 — Ten stacked contract breaks, each masking the next

I wrote an auto-discovery loop that patches each violation and retries. Order of discovery:

  1. PPO_OBS_SIZE=84 vs 106 feature names — import-level
  2. market_data.D1 supplies 20 bars; min_bars_htf requires 30
  3. experts['seasonality'] missing proposal
  4. risk_state missing portfolio_risk
  5. risk_state missing risk_budget
  6. account_state missing current_step
  7. account_state missing max_steps
  8. account_state missing pnl_trend
  9. account_state.episode_return is None — not even in the validator's own required list
  10. env writes market_predictions.latest_predictions.confidence; builder reads market_predictions.model_confidence

H4 supplies exactly 30 bars against a 30-bar minimum — one off-by-one from an eleventh break. Conclusion: the 106-dim observation path has never executed successfully. Fixing only item 1 converts silent zeros into a hard crash on first reset().

F2 — Fail-silent is systemic, not incidental

Statically verified 2,529 except Exception or bare-except sites across 206 files. Concentrated in exactly the components that must never fail quietly:

Three independent silent-degradation paths are confirmed: the observation fallback, the orchestrator's ImportError skip, and _normalize_obs's pad/truncate.

F3 — Evaluation cannot distinguish skill from beta

Empirically measured XAUUSD gained +149.8% across the full sample. Train segment +87.9%, holdout +32.8%. Both are strong uptrends, and the holdout is additionally used for curriculum promotion, so it is a validation set, not a test set. A policy that simply learns long bias will appear to generalize. No result from the current protocol can be believed.

F4 — Reproducibility is broken at the root

The feature CSVs are clean and causal, but the script that produced them is not in version control (it lived in scripts/, which .gitignore excludes along with tests/ and docs/). The features cannot be regenerated, extended, or audited for a new instrument. Combined with a requirements.txt that cannot install, no clean-room reproduction of any result is currently possible.

09RL architecture assessment

Action space

Statically verified 10 discrete actions: HOLD, LONG × {0.35, 0.60, 0.85, 1.10}, SHORT × {…}, CLOSE. Size buckets scale risk_per_trade_pct = 0.003, so €105–€330 risk on a €100k account against a hard_stop_loss_eur = 220.

The agent cannot set a stop distance, a target, a trailing rule, or a partial close. It exits only at market on a bar boundary. For a prop-firm mandate whose entire objective is drawdown control, the single most important risk lever is absent from the action space — and the simulator could not score it correctly anyway. Adding stop distance is justified; adding targets, partial closes and trailing simultaneously is not, given the sample budget. Recommendation: add one dimension (stop distance, 3–4 buckets), and only after the intrabar simulator exists.

Algorithm fit

PPO is on-policy and sample-hungry — the worst match for a ~3,223-sample information budget. It was chosen before the budget was measured. The defensible order is: establish supervised and bandit baselines first, then justify PPO by margin, not by assumption.

Recommended deterministic intrabar policy

Without tick or M1 data, the honest rule is pessimistic and deterministic:

  1. If a bar's range touches both stop and target, assume the stop filled first.
  2. Mark equity for drawdown purposes at the bar's adverse extreme (low for longs, high for shorts), not the close.
  3. Fill stops at the stop price plus slippage; fill targets at the target price with no price improvement.
  4. On gaps, fill at the open, never at the intended level.

Acquiring M1 data for XAUUSD would let rules 1 and 2 be replaced by measurement, and is the single highest-value data purchase available.

Binding architectural decisions

  1. Simulation clock first. Recover simulation_time.py; make set_simulation_mode(True) forbid time.sleep, thread spawning and wall-clock staleness inside any module reached by training. This is a precondition for decisions 2–3.

  3. One expert implementation — chosen by ablation, after the clock lands. Both candidates become runnable in training; E12 picks the winner on out-of-sample value, not line count. Seasonality exists only in modules/voting/experts/ and must survive either way.
  4. Drawdown as a constraint, not a reward term. Lagrangian PPO or a hard veto layer. A penalty is negotiable by the optimizer; a constraint is not.

  6. Memory starts deterministic. A compact trade-history vector, not a learned encoder, until an ablation proves the learned version wins.
  7. Risk vetoes live outside the policy so they cannot be optimized around and remain identical in live.
  8. Fail-closed everywhere. Any critical component that cannot initialize stops the process. Non-critical diagnostics may degrade, and must say so loudly.

14Questions We Must Answer Before More Coding

  1. Where is the edge expected to come from? No document in the repository states a market hypothesis. Without one, RL is an undirected search over ~3,223 samples. This is the single most important unanswered question, and it is not a coding question.
  2. Should the system discover alpha or manage it? The evidence in §8 argues strongly for managing — RL as sizing/filtering over a validated signal. Discovery needs far more data than exists.
  3. Is M15 XAUUSD the right venue? It is among the most heavily mined retail timeframe/instrument pairs. Was it chosen for an edge reason or for data convenience?
  4. Can the +149.8% regime bias be escaped? Either longer history, more instruments, or explicit regime holdouts. Without one of these, no backtest number means anything.
  5. What are the real live constraints? Which prop firm, what exact DD rules, what minimum stop distance, what commission schedule, what execution latency? The simulator currently encodes assumptions, not a specification.
  6. Is M1 or tick data obtainable? It would replace the pessimistic intrabar guess with measurement — the highest-value data acquisition available.
  7. Does the agent need 106 inputs? E4/E5/E6 will answer it. Prior: 44 market dims plus a small account/constraint block will match or beat the full vector.
  8. Does memory improve decisions or only complexity? 11,307 LOC currently contribute nothing. E7 decides.
  9. Do experts add orthogonal information beyond indicators already in the 58-column feature set? Much of the expert output is a re-derivation of RSI/MACD/ADX that the agent already sees.
  10. What profitability and drawdown are economically meaningful? No target is stated. Without a threshold, "better" is undefined and every result is arguable.
  11. What evidence would invalidate the project? I propose: failing E20 (regime holdout) or E19 (1.5× cost stress). Agreeing this in advance prevents moving the goalposts later.
  12. What would justify continuation? Beating buy-and-hold and every §8 baseline on risk-adjusted return, across ≥5 seeds, on an untouched split, after 1.5× costs.
  13. Is the 5× spread widening a regime change or a broker change? The recording method is identical (100% match on overlapping bars), so the widening is real — but whether it reflects the 2026 volatility regime or a change in FTMO's pricing determines whether to train against 8-point or 41-point costs. Pull FTMO's spread history across the full period to settle it.
  14. Should the real modules run in training at all? Once the simulation clock exists, they can — but they may be too slow. E23 measures both value and wall-time. If they cost 3× step time for <0.15 Sharpe, keeping the synthesized mixins becomes the evidence-backed answer, and the duplicates can finally be deleted rather than merely archived.
  15. Which account will actually trade? The data is FTMO; config/live.yaml names MetaQuotes-Demo through a nonexistent path; the terminal is logged into FTMO-Demo (1514121325). Prop-firm rules, costs and DD semantics differ per account type, and the simulator should encode the real one.

Assessment of the prior 10–15% estimate

Directionally correct, mechanically wrong. It was driven by defect count, and every one of those defects is repairable — which would argue the number should rise sharply after repair. It does not, because the real constraint was never the bugs: it is ~3,223 effective samples against a 106-dimensional input, over a single instrument, in a single directional regime. My post-repair estimate for the current architecture (12–20%) lands near the prior number by a different and more durable route.

Revision from the data investigation: two forces, opposite directions

Upward: a real out-of-regime test set now exists at zero cost, and the root cause of the architectural split (F0) turns out to be solvable with 658 LOC already written. Both raise confidence in the process.

Downward: the current XAUUSD spread regime is 5.1× wider than the training data (median 41 vs 8 points), and XAUUSD swap is −67.72/lot/night on longs, entirely unmodelled. Against a mean absolute M15 move of 1.55, a 41-point (0.41) round-trip spread plus commission consumes a much larger share of every trade than the simulator assumes.

Net effect on live-profitability probability: roughly neutral, with far tighter error bars. The estimates stand at 12–20% for the current architecture and 25–35% for RL-as-sizing. What changed is that both are now testable rather than speculative — E20 and E24 can be run before committing to the expensive integration work.

What would materially raise these numbers

  1. A stated, testable edge hypothesis. The largest single lever, and it costs no code.
  2. Restructuring RL as sizing or filtering over a validated signal: +10–15 points.
  3. More independent data — more instruments, longer history, or a genuine bear regime: +5–10 points.
  4. Cross-asset macro context, the most plausible orthogonal signal for gold: +3–8 points.
  5. M1/tick data, converting simulator assumption into measurement: +3–5 points.
  6. Passing E20 (regime holdout). Until this passes, treat every other number as provisional.
