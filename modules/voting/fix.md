High-Level Architecture Map
The voting subsystem is organized as a pipeline of voting experts and coordinating stages. Multiple expert modules (e.g. MomentumExpert, TrendExpert, SeasonalityRiskExpert, ThemeExpert) independently analyze market data and produce per-instrument vote proposals. Each expert’s output is a set of proposed actions (e.g. long/short/flat) with confidence levels for each instrument (EURUSD, XAUUSD). These experts leverage a common SmartInfoBus messaging layer to publish their proposals, using standardized keys for each expert (like <ExpertName>_voting_proposal and <ExpertName>_confidence). The SmartInfoBus acts as the communication backbone, allowing the next stages to discover and aggregate expert outputs. A CommitteeCoordinator module then collects all expert votes from the SmartInfoBus and aggregates them on a per-instrument basis. The Coordinator runs as a singleton service (to ensure consistent state) and is responsible for determining the combined committee decision for each instrument. It performs tasks such as discovering active voting members, weighting expert votes (optionally by performance), computing consensus/majority across experts, and generating an overall committee thesis. The Coordinator publishes its results back to the bus using keys like committee_decision (overall decision action per instrument), committee_confidence, and committee_consensus, as well as details such as per-instrument decisions and raw proposals from members. Following the coordinator, additional pipeline stages (ConsensusAnalyzer, CollusionDetector, HorizonAligner, FinalArbiter, etc.) may refine the decision. For example, a ConsensusAnalyzer measures agreement strength, a CollusionDetector checks if experts are overly correlated, and a HorizonAligner adjusts signals to trading horizons. These are executed in sequence by the main orchestrator. Finally, the FinalArbiter (or voting kernel) produces the final trade decision per instrument, which downstream modules (PositionManager, Executor) consume for execution. Notably, the system is designed so that each instrument has an independent final decision (e.g. one can be long EURUSD while another is flat XAUUSD), and downstream components handle each instrument separately. The SmartInfoBus keys reflect this pipeline, e.g. committee_votes for aggregated votes, consensus_result for consensus metrics, collusion_result for collusion analysis, and ultimately final_decision or trade_vote for the end decision.
Bug & Error Catalogue
1. Inconsistent vote labeling causes misaggregation: The experts sometimes use custom action labels (e.g. "momentum_long" or "momentum_neutral") in their proposals, which the aggregation logic doesn’t fully recognize. For instance, the MomentumExpert may output an action "momentum_long" for a bullish signal (per its documentation). However, the CommitteeCoordinator’s vote aggregator treats any action not literally equal to "long" or "short" as a flat/neutral vote. This means a "momentum_long" action would be mis-categorized as flat in the vote tally, effectively ignoring a directional momentum vote. This is a critical logical bug: the coordinator’s aggregation code only counts exact "long"/"short" and lumps all other actions (including "momentum_long"/"momentum_short") into the flat category. As a result, certain expert signals might not influence the final decision as intended. 2. Legacy vs. current action naming mismatches: There are discrepancies between documentation, code, and usage of action names such as "flat", "hold", "neutral", and "abstain". The VotingProposal dataclass allows actions 'long', 'short', 'hold', 'abstain', and the system treats flat/neutral/hold as essentially “no position” in practice. However, different parts of the code use different terms: for example, MomentumExpert returns 'flat' in code when no clear signal, even though its documentation refers to a "momentum_neutral" action. The coordinator explicitly ignores a variety of neutral action strings ('abstain', 'neutral', 'hold', 'flat', as well as legacy 'momentum_neutral', 'trend_neutral', etc.) by mapping them all to HOLD or filtering them out. These inconsistent labels are error-prone – if an expert uses a new or undocumented label for “no action”, it might not be caught by the ignore list, or it might be filtered unexpectedly. The presence of legacy action strings in the ignore list (e.g. 'seasonal_neutral', 'theme_neutral') suggests the implementation has undergone naming changes that weren’t uniformly applied, leading to potential mismatches between what the expert outputs and what the coordinator expects to filter. 3. Multiple bus key aliases and duplication: The code uses multiple aliases for the same data on the SmartInfoBus, increasing the risk of inconsistencies. For example, SeasonalityRiskExpert’s output publishes three redundant sets of proposal/confidence keys: "SeasonalityRiskExpert_voting_proposal" (canonical), "seasonality_voting_proposal" (alias for compatibility), and even "seasonal_voting_proposal" (another alias) – all carrying the same content. Similarly, both "ThemeExpert_voting_proposal" and "theme_voting_proposal" are set. This duplication is error-prone: a mistake in updating one alias (or a consumer listening to the wrong alias) could lead to missed or inconsistent information. It also bloats the bus with redundant entries. The CommitteeCoordinator compensates by checking for these alternates (it appends 'momentum_voting_proposal' if the expert name is MomentumExpert, etc.), but this approach is fragile. If an expert fails to set one of the pairs or if a new expert isn’t hardcoded into _voter_key_pairs, the coordinator might miss that expert’s vote entirely. In short, the reliance on parallel key naming schemes increases the chance of contract violations (e.g. one part of the system expecting a key that isn’t provided in all cases). 4. Misuse of data structures and leftover code paths: There are signs of partially refactored logic that could lead to runtime issues. For example, MomentumExpert appears to have two modes of operation in the code – a new per-instrument process method and an older _generate_expert_specific_proposal method – with the latter relying on instance variables like self.close_history, self.high_history, etc.. The expert’s _expert_specific_init initializes both a per-instrument state dictionary and legacy single-instrument deques (self.close_history = deque(maxlen=200) etc. marked “legacy”). If the old code path is inadvertently used (or not fully disabled), it could cause inconsistent behavior (e.g. mixing data between instruments or using stale data). This duplication suggests the refactoring is incomplete, and running the wrong code path could introduce bugs (like index errors or using an empty close_history). It’s error-prone to maintain two sets of state – one of which is supposed to be superseded by the other. At best, it’s dead code; at worst, it might execute in some configurations and produce incorrect results. 5. Overly broad exception handling and silent failures: The code frequently wraps large blocks in try/except Exception and falls back to defaults, which, while preventing crashes, can mask the underlying error. For instance, the MACD calculation in MomentumExpert catches any exception and just returns (0.0, 0.0, 0.0). If the MACD failed due to a logic bug (say a miscomputed index), the system would quietly continue in a degraded state (effectively ignoring the MACD signal) without flagging a clear error beyond a log message. Similarly, the RSI calculation catches exceptions and returns 50.0 (neutral), and many other helper methods do the same (OBV returns 0 on exception, etc.). While the module does log warnings/errors in many places (e.g. logging a warning if price data update fails, then returning False), some fallback paths use pass (e.g. in publishing baseline bus keys) or otherwise continue silently. This pattern can lead to error conditions that are hard to detect from outside. For example, an indicator consistently throwing an exception would result in a constant default output (like RSI always 50), potentially degrading signal quality with little visibility – the system degrades gracefully but without alerting that something is fundamentally wrong beyond a log line. 6. Minor numerical issues: In general the numerical computations are carefully bounded (clamping values between 0 and 1, etc.), but there are a few subtle issues. For instance, the consensus aggregator uses Python’s max() on a dictionary of scores to determine the winning action. In the event of a tie in scores, Python’s max will return the first encountered key – meaning if long and short scores are exactly equal, it will choose “long” (since the dict is iterated in insertion order). This could introduce a slight bias towards LONG in perfect-tie scenarios. Another example: when computing recent OBV momentum, the code divides by abs(obv_recent[0]) + 1e-10 to avoid division by zero. If obv_recent[0] is extremely small (on the order of 1e-10 or smaller), this can still blow up the result. These are edge cases and not likely to cause runtime crashes (due to the safeguards), but they can produce spurious outputs. They illustrate the kind of error-prone corner cases that should be documented or handled (e.g. making the tie-breaking in voting explicit, or setting a floor for denominators beyond just adding 1e-10).
Logic & Contract Mismatches
Action naming vs. documented contract: There is a clear mismatch between the documented actions for experts and what the system’s contract expects. Documentation for experts like MomentumExpert and TrendExpert defines custom action names such as "momentum_long" / "momentum_short" / "momentum_neutral" for their signals, but the broader voting system (bus contracts and coordinator) treats actions generically as "long", "short", or neutral/hold actions. In practice, the experts often revert to using "flat" for no-action (the MomentumExpert returns {'action': 'flat', 'signal_strength': 0.0, ...} when insufficient data or no signal). The coordinator’s ignore list even comments that new experts use 'long'/'short'/'flat' instead of legacy labels. This means there’s a disconnect between the intended design (with rich action names per expert type) and the implemented contract (which now expects standardized actions). The presence of both 'flat' and 'momentum_neutral' in different parts of the system indicates a contract inconsistency: some code expects one, some the other. This could confuse consumers of the bus or developers – e.g. a monitoring tool might see an action "momentum_long" and not realize it essentially means a long recommendation, or worse, treat "momentum_long" as an unrecognized action. The contract should be consistent: either experts output standardized actions (with maybe a separate field for expert type or reason), or the aggregation logic should fully support expert-specific action labels. Right now it’s caught in between (supporting some legacy names to ensure nothing breaks). Signal strength vs. magnitude: The system uses different terminology for essentially the same concept in different places, which can lead to confusion. In expert proposals (VotingProposal), the field is called signal_strength, whereas in per-instrument proposals (InstrumentProposal) the analogous field is magnitude. These both represent the intensity of the signal (0.0 to 1.0). The dual naming doesn’t break functionality (since they are used in different contexts), but it is a conceptual mismatch that can lead to errors. For example, the PerInstrumentVote dataclass’s to_dict packs the global action under 'action' and the max magnitude under a nested 'proposal': {'magnitude': ...} for legacy compatibility. Meanwhile, an expert’s own output dict might include 'signal_strength' in its proposal. This overlapping usage could confuse a developer reading the code or integrating another component – one might inadvertently use signal_strength where magnitude was intended or vice versa. It also complicates the coordinator logic: the coordinator normalizes incoming votes by wrapping raw proposals into a dict with 'vote': {…} and 'confidence': …. If an expert’s vote already had a nested structure, there’s potential for double-wrapping or losing information. Ensuring a clear contract (e.g. always use 'confidence' and 'signal_strength' at the top level of an expert vote, and use 'magnitude' only inside InstrumentProposal for internal calc) would simplify understanding. As it stands, the system relies on internal knowledge of these fields to translate correctly. Per-instrument vs. global output confusion: Each expert is supposed to produce per-instrument outputs, yet the interfaces mix per-instrument and global data in a sometimes confusing way. The PerInstrumentVote structure contains a dict of proposals by instrument and a “global” action/confidence for legacy consumers. Experts follow this by publishing both – e.g. MomentumExpert returns a dict that includes its per-instrument votes and repeats the best action as MomentumExpert_voting_proposal with a single action/confidence. Consumers need to be careful: reading just MomentumExpert_voting_proposal gives only the highest-confidence idea, not the full picture if the expert had differing signals on instruments. Conversely, reading just MomentumExpert_per_instrument_votes is the correct detailed view, but older parts of the system or logs might only show the global field. This duality is a contract smell – some parts of the code assume a one-expert-one-proposal model, while newer parts assume one-expert-multiple-proposals. For example, the coordinator’s _collect_expert_votes primarily collects each expert’s global vote (via <name>_voting_proposal and <name>_confidence) and only uses the per-instrument details in a later aggregation step. This could lead to scenarios where the global summary misses nuance (say an expert is long EURUSD, short XAUUSD – the global might just pick one). The mismatch is that the design promises full per-instrument voting, but the implementation still partially operates in a global vote mindset for consensus building. It’s manageable (because ultimately the coordinator does break out per-instrument decisions in _determine_committee_decision) but it complicates the contract and increases the chance of logical errors if a developer isn’t aware of which representation to use. Documentation vs implementation gaps: Several configuration fields and features in documentation do not have a clear effect in code, indicating possible contract violations or at least unfulfilled promises. For example, documentation for experts claims “adaptive thresholds based on volatility” for momentum and trend, but in the code the thresholds (e.g. momentum_threshold = 0.015 for MomentumExpert) are hardcoded or read from static config, with no adaptive logic that adjusts to current volatility regime. Similarly, TrendExpert’s doc mentions support/resistance awareness and multi-timeframe alignment【1†L139-L147}, but in code, aside from computing some moving averages and ADX, there’s no explicit multi-timeframe handling or dynamic S/R logic visible (just a fixed trend_threshold = 0.003 for all instruments)【32†L23-L31】. This represents a contract mismatch between the intended behavior and actual behavior. Fields like confidence_decay or signal_threshold appear in the config (perhaps for smoothing confidence over time) but are not visibly used in the provided code. In short, the code as implemented may not live up to the “contract” implied by the system’s design docs. This can be misleading and dangerous in a mission-critical system – for instance, one might believe the momentum thresholds auto-adjust, when in reality they might need manual tuning per instrument. Such discrepancies should be resolved either by implementing the documented feature or adjusting the documentation/contract to match reality.
Per-Instrument Behaviour (EURUSD vs XAUUSD)
Each expert module handles multiple instruments in isolation, aiming for clean state separation between EURUSD and XAUUSD (and any other configured instruments). The code explicitly normalizes instrument symbols (e.g. mapping "GOLDUSD" to "XAUUSD") to ensure consistency, and it maintains independent data containers per instrument. In MomentumExpert and TrendExpert, for example, an instrument_state dictionary is initialized with a key for each instrument, each holding its own price and indicator history deques. As the momentum expert’s process iterates through self.instruments, it extracts market data for each one and updates that instrument’s slice of state separately. This design avoids any cross-talk: prices, RSI values, OBV calculations, etc. for EURUSD are stored and computed separately from XAUUSD. The code verifies this by normalizing the instrument name when setting or getting proposals in the PerInstrumentVote; for instance, PerInstrumentVote.set_proposal will normalize the proposal’s instrument and use it as the dict key. So even if an instrument name comes in lowercase or with a suffix, it maps to the same canonical key, preventing duplicates or overlaps. Importantly, after processing all instruments, the expert does not produce a single blended action – it keeps per-instrument proposals. The global action field in PerInstrumentVote is chosen simply as the highest-confidence proposal among the instruments to satisfy legacy consumers. This means the expert might internally decide, say, EURUSD: long (0.8 confidence) and XAUUSD: short (0.6 confidence). It will report both, and mark the global action as “long” with 0.8 confidence (since that was the higher) – but crucially, it still provides the XAUUSD short proposal in the per-instrument dict. Downstream, the CommitteeCoordinator reads each expert’s proposals for each instrument to aggregate them, ensuring, for example, that a short vote on XAUUSD from one expert isn’t overshadowed by a long vote on EURUSD from another. The final decisions are kept instrument-specific: the coordinator’s output includes committee_decisions_by_instrument mapping each symbol to an aggregated decision, and downstream execution logic is per instrument. The implementation takes care to prevent state contamination. For instance, momentum’s indicator history deques (price_history, rsi_history, etc.) are stored in the instrument_state under each symbol, not in shared attributes. Within one run of process(), after updating an instrument’s state and computing its proposal, that proposal is immediately stored (via per_instrument_vote.set_proposal) and the loop moves on – there’s no reuse of variables that isn’t re-initialized for the next instrument. Logging and bus outputs also include the instrument context where relevant (the SeasonalityRiskExpert, for example, includes the instrument in its rationale messages and keys). This design ensures that heavy computation for one asset (like a large spike in gold volatility) doesn’t directly skew the signals of another (EURUSD) except via any shared logic in the coordinator. One potential area of risk is the global decision heuristic – choosing the highest-confidence instrument’s action as the expert’s single “vote.” In a scenario where experts are split (one instrument long, one short), the coordinator might receive contradictory global votes from different experts (one voting “long” based on EURUSD, another “short” based on XAUUSD). However, since the coordinator eventually aggregates by instrument, it will reconcile these properly per instrument. It’s just that the intermediate consensus steps need to handle such divergence. The code provides for that by ultimately using aggregate_all_instruments(votes, ...) to compute an AggregatedInstrumentDecision for each instrument. The good news is that each instrument’s logic is isolated enough that we can reason about and test them independently, and any cross-contamination would likely be a clear bug. So far, we see none – the implementation correctly uses separate keys, separate state, and copies data structures when outputting (to avoid accidental mutation). Each expert even tags its proposals with the instrument name (e.g. InstrumentProposal.instrument field) which serves as a sanity check when aggregating.
Trading Logic Quality for XAUUSD and EURUSD
Indicator choices and thresholds: The experts employ a rich set of technical indicators – MomentumExpert looks at ROC, RSI, MACD histogram, Stochastic, OBV, etc., while TrendExpert uses multiple moving averages, ADX, etc. These are standard and sound choices for FX and commodities. The combination logic (summing weighted scores for bullish/bearish signals) is reasonable, but the thresholds and weights may not be one-size-fits-all for EURUSD vs XAUUSD. For instance, MomentumExpert uses a fixed momentum_threshold = 0.015 (1.5% price change) to decide if momentum is strong. A 1.5% move in EURUSD is extremely large (might happen only on major news), whereas a 1.5% move in XAUUSD is not unusual. Using the same threshold for both means the momentum model will trigger far more often for gold than for EURUSD, which might be unintended. Similarly, TrendExpert’s trend_threshold = 0.003 (0.3% price move relative to support/resistance, presumably) is tiny for gold (which can move >1% in a day) but might be acceptable for EURUSD’s daily range. Without instrument-specific tuning, the model might flag nearly every gold move as a trend while being too conservative on EURUSD. This suggests the need for calibration: either dynamic thresholds based on volatility (e.g. a fraction of ATR) or separate config values per instrument. Shared parameters vs. instrument-specific parameters: Currently, the configuration uses mostly shared parameters for both instruments (the default self.instruments = ['EURUSD','XAUUSD'] and one set of thresholds/periods). The code does not adjust things like RSI period or overbought level for different instruments – which is probably fine (14-period RSI at 70/30 is standard everywhere). However, other parameters like OBV volume confirmation could differ: volume patterns in XAUUSD futures can be spikier than FX volume. The MomentumExpert’s volume confirmation logic and multipliers are the same for both, meaning it expects the same relative volume surge to confirm a move. If gold’s volume behavior is inherently different, this might misjudge confirmation. In practice, these models would benefit from instrument-specific hyperparameters. For example, one might want a higher momentum threshold for gold (maybe 0.025) and a lower one for EURUSD (0.01) to equalize signal frequency. Or TrendExpert could use different moving average lengths for gold vs FX given gold’s often more mean-reverting intraday behavior compared to currency trends. Currently, such differentiation requires running separate expert instances with different configs, which the architecture supports in theory (config could override per instrument), but it’s not built-in. A robust solution would be a configuration system where key parameters are keyed by instrument or asset class. Notably, the SeasonalityRiskExpert and ThemeExpert hint at this: they map instruments to asset classes ('forex' vs 'commodity') and could apply different logic based on that. Indeed, SeasonalityRiskExpert has a small example: if a composite seasonal score is slightly bearish but the instrument is gold, it chooses to return “flat” (neutral) because gold behaves differently (“slight bearish but gold – neutral”). This is a hard-coded adjustment that acknowledges gold’s unique nature. We should extend that philosophy systematically to the trading logic parameters. Adaptability and regime awareness: The quality of signals also depends on adapting to regime changes (volatility regimes, trending vs ranging markets). The ThemeExpert is intended to capture macro regime (risk-on/off, volatility high/low) and could feed into weighting other signals, but currently, it just produces its own vote. The Momentum and Trend experts themselves do not explicitly modify thresholds by volatility in code (despite documentation). Without adaptation, a period of ultra-low volatility in EURUSD might not trigger any signals (because ROC stays below 0.015), whereas a volatile period might trigger too many false signals for gold. Ideally, thresholds like momentum_threshold and trend_threshold should be scaled by recent volatility (e.g. a multiple of ATR or standard deviation). Since the code doesn’t do this, trading performance could suffer when market conditions shift. Nonetheless, the overall logic is comprehensive for both assets: using multiple indicators should reduce false positives (e.g. requiring confluence: momentum won’t signal long unless ROC, RSI, MACD etc. collectively tilt bullish). The experts also incorporate safeguards: e.g., TrendExpert monitors ADX (trend strength) and won’t give a high-confidence trend signal in a ranging market (if ADX low, the scores would come out weaker). These mechanisms benefit both EURUSD and XAUUSD, but the scale of signals likely needs adjustment per instrument. Recommendation: Introduce a configuration structure for instrument-specific parameters. This could be as simple as allowing self.config['momentum_threshold_EURUSD'] vs ..._XAUUSD and using those if present. Or calibrate automatically: e.g., multiply the threshold by the ratio of current ATR to a baseline ATR. The SeasonalityRiskExpert and ThemeExpert already differentiate between 'forex' and 'commodity' in some internal rules – a similar approach could let Momentum/Trend adjust sensitivity for gold (commodity) vs FX. This would ensure that a medium move in gold isn’t overhyped, and a significant move in EURUSD isn’t underrepresented. In terms of trading strategy soundness, the combination of momentum, trend, seasonality, and theme experts should provide a holistic view (technical + fundamental-ish signals). Each expert on its own seems logically sound. The momentum model’s use of divergence detection, volume confirmation, and multi-timeframe checks are advanced features that, if properly tuned, can give high-conviction signals (the code tracks counts of bullish/bearish divergences, etc., which could be later used for confidence). The trend model’s use of multi-length MAs and ADX is classic and effective in FX when tuned. The key is ensuring the parameters are tuned to the instrument’s nature, which at present would likely require manual adjustment. A configuration-driven approach or even a learning component (to adjust thresholds based on historical hit rates per instrument) could greatly enhance the quality for each asset class. Finally, it’s worth noting the volume factor: FX volume is often a proxy (tick count or aggregated from multiple liquidity providers), whereas gold has exchange volume. The MomentumExpert’s OBV and volume confirmation assume volume data quality; in FX that data can be noisy. It might be that volume-based signals are more reliable for XAUUSD than for EURUSD. In testing, we should watch whether the volume confirmation adds value for EURUSD or just noise. This again speaks to possibly weighting that feature differently per instrument (e.g. down-weight volume in FX momentum signals). Currently, such differentiation is not implemented, but the need for it is a consideration in evaluating strategy quality.
Robustness & Error Handling
The voting subsystem is built with robustness in mind – it’s designed to degrade gracefully under adverse conditions, rather than throw exceptions or produce malformed outputs. Several patterns in the code support this:
Graceful degradation on error: If anything goes wrong within an expert’s process, the base class traps the exception and returns a safe, degraded output. The _record_error and _degraded_output mechanism in VotingModuleBase ensures the module still returns a well-formed result with an 'action': 'abstain' (or 'flat') and a low confidence (0.1). The degraded output includes a reason message so it’s traceable. This prevents a runtime error in one expert from crashing the whole system – instead that expert just votes abstain for that cycle. The coordinator similarly wraps its vote collection and decision logic in try/except; if an unexpected error occurs, it logs an error and returns an empty vote list or safe defaults. This means the system will fail to a neutral stance rather than making a wild trade or halting execution.
Handling of missing or bad data: The experts check for missing inputs and insufficient history at runtime. For example, MomentumExpert verifies it has enough price bars for the largest ROC period; if not, it logs a warning and returns a flat proposal for that instrument. If the SmartInfoBus doesn’t have the required market data or features for an expert, the expert logs a warning and outputs a neutral/hold signal (via a _neutral_output helper). This ensures that data unavailability results in a cautious no-action rather than an error or a random guess. Similarly, many indicator calculations have default paths – e.g., the RSI function returns 50.0 (neutral mid-value) if there’s any calculation error, and the stochastic function returns (50.0, 50.0) if not enough data or any exception. These defaults are chosen to be neutral (50 is the center of RSI/Stoch range) so that a failed calc doesn’t bias the signal to long or short.
Clamping and validation: All confidence and strength values are clamped to valid ranges (0.0–1.0 for confidence/intensity, 0–100 for RSI, etc.). The VotingProposal dataclass’s __post_init__ ensures any provided confidence or signal_strength that went out of bounds is clipped inside [0,1]. Throughout the code, after computing metrics they often do float(np.clip(...)) to avoid propagating NaNs or infinities. This is a defensive practice that keeps outputs within expected bounds even if something anomalous happens in the math.
Logging and diagnostics: The module makes heavy use of logging at different levels. Warnings are logged for non-critical issues (like “[MOMENTUM] No market data or features available” warning before returning neutral). Errors are logged with stack traces or pinpoint analysis for unexpected exceptions (the error_pinpointer is used to analyze errors and log them with context). Additionally, the system logs important state changes (e.g., the coordinator logs its initialization with the configured thresholds and settings, and logs each vote it collects and filters in debug mode). These logs are crucial for robustness because they allow a developer/operator to understand why the system is in a degraded state or why it filtered certain votes. For example, if an expert is consistently returning neutral due to missing data, the warnings will make that clear; it won’t fail silently.
Fault tolerance in SmartInfoBus usage: The SmartInfoBus integration is designed to not interrupt processing if the bus is unavailable or if a particular set/get fails. In _setup_smart_bus, if the InfoBus connection fails to initialize, the code falls back to a dummy bus object that will raise on use, ensuring that if someone tries to use it, it fails loudly at that point. Bus set operations in non-critical sections are often in try/except – for instance, the CommitteeCoordinator’s baseline publishing is wrapped in a try so that if the bus store fails, it just passes, under the assumption that failing to publish a baseline metric is not worth stopping the system. This way, a momentary bus issue doesn’t bring down the module. The trade-off is that such failures are not strongly reported (just a debug log or silent), but the philosophy is clearly to keep things running.
Edge cases: One area to watch is that while the system handles known failure modes, there could be unknown edge cases. For example, if an expert’s config is set in a weird way (say someone sets an RSI period of 1), would the code handle it? Probably yes (it would just compute trivial RSI). If market_data contains NaNs, many of the numpy operations (np.diff, np.mean) will result in NaN outputs that might then get clipped to 0 or 0.5 by default. The code doesn’t explicitly check for NaN in inputs, but the downstream clamping or default returns typically neutralize their effect. Another potential issue is time synchronization – not exactly robustness, but if experts are producing signals at slightly different times, the coordinator’s max_vote_age_s setting (staleness threshold) will drop votes older than e.g. 5 seconds. This is a robustness feature to ignore stale expert data. We should verify that experts update their bus outputs every tick; if one expert is slower and misses a tick, the coordinator might treat its previous vote as stale and ignore it, which is actually desired (better to ignore an out-of-date vote). Graceful handling of partial failures: If one expert goes into emergency mode (say it encounters repeated errors and always returns abstain), the coordinator will simply see that expert as always voting “hold” with low confidence and the other experts will dominate the decision. The system doesn’t have a specific alert for “expert so-and-so is in degraded mode” beyond the log and perhaps a SmartInfoBus flag (emergency_status in the expert’s output). It might be wise in future to surface that via the bus to a monitoring UI. But functionally, the system continues to operate. In summary, robustness is a strong point of this module: it anticipates missing data, out-of-range values, and exceptions, handling each in a controlled manner. The result is that the trading strategy will default to “do nothing” in uncertain scenarios rather than do something erratic. The logs and bus outputs (like the _thesis field each expert sets explaining its rationale) give insight into those decisions, which aids debuggability. The only caution is that by suppressing errors and always outputting something, a subtle bug could go unnoticed – you’d see more “flat” votes but have to dig in logs to find the cause. Regular monitoring of the logs or a dashboard for expert health is advisable to catch such situations.
Refactoring & Improvement Plan
Refactoring the voting subsystem should be prioritized by severity: Tier 1 – Critical fixes (bugs that can alter decisions or stability):
Unify action labels for voting outcomes: Eliminate the confusion between "momentum_long" vs "long", "trend_neutral" vs "flat", etc. The experts should output standardized actions (perhaps just "long", "short", "flat" for neutral, and "abstain" if not participating). Any notion of the expert’s flavor can go into a separate metadata field (e.g. expert name already is in the proposal). This will fix the bug where the CommitteeCoordinator misinterprets custom actions. Concretely, MomentumExpert and others should be refactored to set proposal['action'] to "long" or "short" (instead of "momentum_long"), and use a field like proposal['reason'] or metadata to note it was momentum-driven. The coordinator’s ignore list and mapping can then be simplified (no need to handle legacy strings) – reducing the chance of an unrecognized string slipping through. This change ensures that all directional votes are counted correctly. It’s critical to do this carefully and possibly provide backward compatibility (the system could still publish the old keys or labels for a few versions if other components expect them, but internally move everything to one vocabulary).
Fix aggregator handling of expert outputs: Currently, the coordinator mainly reads each expert’s global proposal and confidence, then later aggregates per instrument. This can be refactored such that the coordinator directly uses the detailed per-instrument votes from each expert to form the committee decision. A safer design is: each expert publishes a PerInstrumentVote structure (which it already does as <Expert>_per_instrument_votes on the bus) and the coordinator collects those, then calls aggregate_all_instruments on them. This ensures that if an expert has divergent opinions on different instruments, those are properly accounted for in the consensus. It would remove the need for the coordinator to guess an expert’s action from <name>_voting_proposal which loses information. In implementation terms, instead of _voter_key_pairs only having proposal/confidence, we could extend it to fetch <Expert>_per_instrument_votes from the bus. This is a significant change but would align the code with the design principle “votes are aggregated per-instrument by CommitteeCoordinator”. Until this is done, it’s critical to at least document the current behavior to avoid logic bugs – but making this change will improve correctness in multi-instrument voting.
Remove or reconcile dead/legacy code paths: Any duplicated logic that isn’t truly needed should be pruned to avoid accidental use. For example, if MomentumExpert’s new process supersedes _generate_expert_specific_proposal, then the latter (along with legacy attributes like self.close_history) should be removed or clearly marked as deprecated (and ensured not to run). In the provided code, large sections appear to be refactored but left in place (perhaps commented out). This needs cleanup: deleting or fully commenting out the unused parts will avoid confusion. If some experts like SeasonalityRiskExpert and ThemeExpert are still using the BaseModule with their own custom process, consider refactoring them to use the common VotingExpertBase to reduce code duplication (more on that in Tier 3). For now, eliminating conflicting code ensures the system executes what we expect and not an outdated function.
Tier 2 – Logical inconsistencies and maintainability:
Consolidate SmartInfoBus key usage: The practice of writing multiple aliases for the same data should be minimized. Define a single canonical key for each piece of data and stick to it. If backward compatibility is required (perhaps older consumers expect theme_voting_proposal instead of ThemeExpert_voting_proposal), implement the aliasing in the SmartInfoBus layer or maintain a mapping internally, rather than having every expert set both. For instance, the coordinator’s _voter_key_pairs can be expanded or made data-driven: instead of hardcoding alias pairs, use a dictionary or configuration that lists expert name aliases. Even better, since the code already has a VotingBusKeys class with static helpers, we could use VotingBusKeys.expert_proposal(name) to generate keys consistently. Reducing hardcoded strings will ensure that if an expert’s name changes or a new expert is added, one doesn’t have to scour the code to add new alias handling. The SeasonalityRiskExpert’s output can also be trimmed – for example, do we need both "seasonality_risk_analysis" and three layers of "seasonality_analysis" aliases? Perhaps we keep one detailed analysis dict under a standard key (say <Expert>_analysis), and drop the rest. Every extra alias is an opportunity for inconsistency (one might be updated while another is not).
Clarify the output contract for proposals: All experts should return their output in a uniform structure. As it stands, some experts (Momentum, Trend via VotingExpertBase) return a dict with keys 'voting_proposal', 'confidence', etc., while SeasonalityRiskExpert’s _neutral_output returned a dict with keys "SeasonalityRiskExpert_voting_proposal": "flat" (note, a string value, not a dict). We should standardize this so that every expert’s <Name>_voting_proposal value is a dictionary (or dataclass) containing at least action and signal_strength (and optionally confidence if it’s per instrument). Likely the best approach: have experts always output a full VotingProposal or InstrumentProposal data structure. For example, SeasonalityRiskExpert, instead of "flat" (string), should output {'action': 'flat', 'signal_strength': 0.0, 'reason': 'No signal'} or similar structure. This aligns with Momentum/Trend outputs and simplifies parsing. The coordinator normalization code already handles both cases (wrapping a string into a dict), but if we enforce consistency, we can remove that conditional and trust that proposal is always a dict. Consistency here prevents subtle issues (imagine if in one branch an expert returned a dict vs in another returned a string – the coordinator might include/exclude confidence differently).
Improve separation of concerns in experts: Right now, some experts do everything inside process – data fetch, computation, bus publication. Others rely on base class to do some steps. It would be cleaner to refactor expert logic into smaller testable units. For instance, break MomentumExpert’s monolithic _generate_expert_specific_proposal (or the inlined loop in process) into helper methods: _analyze_instrument(prices,...)->InstrumentProposal and possibly reuse that per instrument. This makes it easier to unit test each indicator combination on sample data. Similarly, SeasonalityRiskExpert’s process is quite complex, mixing session analysis, day-of-week, month patterns, etc., then constructing a big output dict with many fields. That could be broken into _analyze_time_patterns(instrument) that returns a structured result, and a separate method to format that into proposals. This refactoring doesn’t change functionality but improves readability and maintainability. It also reduces the chance of error when modifying one part (less interwoven code).
Instrument-specific config and dynamic adjustment: While perhaps not a “bug,” the current lack of instrument-specific tuning is a logical gap. We should introduce a config schema where you can do, e.g., config = {'EURUSD': {'momentum_threshold': 0.01}, 'XAUUSD': {'momentum_threshold': 0.02}}. During expert initialization, override defaults with any instrument-specific values. This could be implemented by storing a dict in the expert and using the appropriate one per instrument in the loop. Alternatively, run two instances of MomentumExpert with different configs (one for EURUSD, one for XAUUSD), but that defeats the design of per-instrument voting in one module. So better to handle it internally. This improvement is medium priority – the system runs without it, but trading performance and clarity will improve with it. It also guards against future expansion: if we add a new instrument (say GBPUSD), we might want a different threshold, and the current design has no easy hook for that besides hardcoding in code or reading from an external config and implementing logic to apply it.
Tier 3 – Code health and maintainability:
Modularize the codebase: The provided code is very large (10k+ lines) and combines many classes in one file. It would be much easier to manage if split into logical modules: e.g., experts/momentum.py, experts/trend.py, experts/seasonality.py, etc., and a coordinator.py, with a clear API between them. The current single file makes it harder to navigate and isolate changes. During refactoring, we should also remove commented-out blocks of old code to declutter (keeping them in version control if needed). The aim is that each expert’s code is in its own class file with perhaps a common base class in experts/base.py. This separation also helps ensure that changes in one expert don’t unintentionally affect another (currently, because everything is loaded in one namespace, there’s a risk of variable name collisions or simply human error reading the wrong part of the file).
Eliminate duplicate utility functions: We noticed that normalize_instrument is defined in multiple places. That should reside in one common utils module to enforce consistency. Likewise, if there are multiple classes defining similar logic for, say, performance tracking or analytic outputs, those could be unified. The code already defines VotingBusKeys, but it might not be fully utilized in all places (strings are still hardcoded). We should refactor to use these constants and helper methods (for example, use VotingBusKeys.expert_proposal(name) instead of f-string each time). This reduces typos and makes renaming easier.
Standardize expert base classes: Currently, MomentumExpert and TrendExpert use VotingExpertBase (which itself extends VotingModuleBase), whereas SeasonalityRiskExpert and ThemeExpert directly extend BaseModule (with custom logic). This leads to some inconsistency in how they initialize and publish results. It would be beneficial to create a unified pattern: possibly have SeasonalityRiskExpert and ThemeExpert also subclass VotingModuleBase or a slight variant of it (since they also produce votes). If their logic is too bespoke, at least adhere to the same output interface. Unifying them under a common base means they’d automatically get the error handling, logging, and bus publishing patterns of the other experts, reducing custom code. We see SeasonalityRiskExpert re-implementing things like its own smart_bus = InfoBusManager.get_instance() and module_name setting – code that VotingModuleBase already handles for others. Unifying this would reduce code and ensure all experts behave consistently in terms of lifecycle (initialization, use of performance tracker, etc.). This refactor is more involved but improves long-term maintainability.
Enhance documentation and comments: Some parts of the code have excellent comments (the top of each expert class has a docstring explaining its methodology, which is great). However, there are complex sections (like the large output construction in SeasonalityRiskExpert’s _neutral_output with many aliases) that could use commentary on why those aliases exist. As we refactor, we should update the documentation to match (for example, if we remove momentum_long action, update the docstring to reflect that actions are just long/short/flat). Clearer documentation of the SmartInfoBus keys – maybe in one place – would also help. Right now, knowledge of keys is spread: docstrings, VotingBusKeys class, and code. We might consolidate a section in documentation that enumerates “For each expert X, it publishes Y_voting_proposal, Y_confidence, and optionally Y_analysis etc.” to solidify the contract.
Testing and monitoring hooks: From a maintainability standpoint, we might add more explicit sanity checks. For instance, after each expert runs, we could assert that the output dict contains certain keys or that confidence is within [0,1] (the latter is already ensured by clamping, but an assert can double-confirm during development). Similarly, the coordinator could warn if it discovered fewer voters than expected or if any expert vote is missing (if an expert is in the config but didn’t produce a vote, perhaps log that). These are not strictly necessary for functionality but aid in diagnosing configuration issues early.
By addressing these refactoring points, we’ll end up with a cleaner, more reliable architecture. Tier 1 items ensure the system’s decisions are logically correct and not hampered by string mismatches or partial data usage. Tier 2 tackles the consistency and reduces complexity (making future bugs less likely). Tier 3 lays the groundwork for easier extensions (like adding new experts or instruments) and easier troubleshooting (since the code will be clearer and better documented). The goal is that the voting subsystem becomes transparent and modify-safe – one where a new developer or quant can adjust a threshold or add an indicator without fear of breaking unseen dependencies or wrestling with inconsistent interfaces.
Test Plan
We propose a comprehensive test strategy encompassing unit tests for individual components, integration tests for multi-component interaction, and property-based tests to ensure invariants hold. The testing will be done in the following structured way: 1. Unit tests for each Expert module:
Indicator computation tests: For MomentumExpert, create synthetic price series to test each indicator helper in isolation – e.g., feed a steadily increasing price series and verify _calculate_rsi returns >70 (overbought), check that _calculate_macd yields a positive histogram when prices trend up, etc. Similarly, test TrendExpert’s moving average crossover logic by constructing a price series where a fast MA crosses above a slow MA and ensure the outcome favors a bullish action. These tests ensure the building blocks behave as expected (and catch any errors in formulas).
Proposal logic tests: Simulate scenarios for each expert and verify the proposed action/confidence. For instance, for MomentumExpert:
Scenario: strong uptrend (prices making higher highs, high volume). We expect process() to output a bullish action (“long”) with high confidence. We’ll feed in a price array that clearly triggers ROC > threshold, RSI > 70, MACD > 0, etc., and assert that the returned voting_proposal action is "long" (or "momentum_long" depending on final refactor) and confidence is close to 0.95 (the cap).
Scenario: choppy sideways prices. Expect output action “flat”/“neutral” with low confidence. For example, alternate prices up and down within 0.1% band, and ensure the expert does not erroneously produce a long/short signal.
Scenario: no data or insufficient data. Call process() with an empty market_data or just a few bars; assert it returns an abstain/flat action with reason indicating insufficient data.
Similar tests for TrendExpert (e.g., feed a price steadily increasing and check for trend_bullish vs a price oscillating and check for trend_neutral/flat).
Confidence calculation tests: Verify that confidence is scaled and bounded. For example, craft a proposal dict for MomentumExpert with various conditions:
One with signal_strength = 1.0 and a lot of confluence flags set (bullish_confluence above threshold, divergence present, etc.) and pass it to _calculate_expert_specific_confidence. Expect the returned float is 0.95 (the max cap).
One with signal_strength = 0.2 and no supporting factors; expect confidence comes out near the minimum 0.15.
If available, test edge cases like passing an unknown action to confidence calc (should just treat as flat and give base confidence ~0.3-0.4).
These tests ensure the scaling logic in confidence calculators is correct and doesn’t produce out-of-range values.
Seasonality/Theme experts tests: Because these incorporate date/time logic, we can simulate specific timestamps:
Feed SeasonalityRiskExpert a date that is Monday 00:30 UTC (Asian session early Monday) for EURUSD and verify it maybe returns a cautious/flat action if Monday historically has lower volatility (given dow_bias data) – basically assert the outputs match the biases in dow_biases config for that weekday.
Test a end-of-year date for XAUUSD (December, where monthly_patterns shows a low trend_strength) and ensure maybe it returns flat or short bias consistent with monthly_patterns[12] which had risk_off.
If we can’t fully predict output due to composite score logic, we at least validate that the output structure contains per-instrument keys and no cross-contamination (e.g., ensure EURUSD’s analysis doesn’t appear under XAUUSD’s keys).
We will also test that their output keys conform to expectations: run SeasonalityRiskExpert with a known scenario and assert that the result dict has "SeasonalityRiskExpert_voting_proposal" and "SeasonalityRiskExpert_confidence" keys, and that their values are correctly typed (e.g., action string or dict, confidence float).
2. Integration tests for the Coordinator and pipeline:
Coordinator vote collection and aggregation: Simulate a set of expert outputs on the SmartInfoBus and run the CommitteeCoordinator’s _collect_expert_votes() and _determine_committee_decision() methods. We can do this by manually populating a fake InfoBus with entries like:
MomentumExpert_voting_proposal = {'action': 'long', 'signal_strength': 0.8}, MomentumExpert_confidence = 0.9,
TrendExpert_voting_proposal = {'action': 'short', 'signal_strength': 0.5}, TrendExpert_confidence = 0.6,
etc., including perhaps a SeasonalityRiskExpert vote.
Then call the coordinator’s process (or the internal methods step by step). We expect:
_collect_expert_votes returns a list of normalized votes (one per expert) where each has 'expert': name, 'vote': {action:..., signal_strength:...}, 'confidence': float. We assert that each expected expert is present and that none are duplicated or missing.
_determine_committee_decision on those votes yields a committee_decision structure. We would verify that for each instrument, the aggregated decision matches the majority or weighted majority. For example, if we provided more experts voting long EURUSD than short, the committee_decision for EURUSD should be long. If weights are applied, we’ll include an expert_weights dict to test weighting logic too (for instance, give MomentumExpert weight 2x TrendExpert and see if that swings the decision).
Test edge case where not enough votes: if we simulate only one expert or provide votes with all action: 'flat', ensure the coordinator possibly returns a committee_decision of abstain/hold. If warmup_ticks is set, simulate fewer ticks than warmup and see if coordinator refrains from a strong decision (maybe consensus_result.consensus_exists=False in output).
We’ll also test that committee_confidence is correctly computed (e.g., if all experts agree long with high confidence, committee_confidence should be high ~ near 1; if they disagree, it might be lower).
End-to-end simulated tick: This would be more of an integration test – feed the entire system a mock market_data tick and run through experts into coordinator. We can create a fake InfoBus object to pass data to experts and collect outputs. For example, create a market_data dict with last prices for EURUSD and XAUUSD, put it in InfoBus, call each expert’s process() (perhaps in asyncio loop if needed, or synchronous if we adjust them for test), then call coordinator’s process(). Verify that the final committee_decision keys exist for both instruments and have reasonable values (not None, and action in {long, short, flat}). This test is to ensure the pieces connect properly – e.g., that experts are indeed reading from InfoBus keys and writing back their proposals such that the coordinator finds them. Essentially an integration sanity check.
Memory and collusion integration: If the memory vote and collusion detection are integrated, we should test those too. For memory:
Put a memory_vote on the InfoBus (e.g., {'signed_bias': 0.2, 'confidence': 0.8, 'neural_risk_hint': 0.5}) and ensure the coordinator’s _add_memory_vote adds an entry “UnifiedMemory” with action long/short as per bias sign. Assert that if bias is small or confidence low, it does nothing, and if bias is significant, the memory vote appears in expert_votes and influences the decision (we might check that with memory vote added, the final decision tilts toward the memory’s action, whereas without it, it was different).
For collusion:

For instance, if MomentumExpert and TrendExpert always both vote long together for several ticks, collusion detector might flag a high collusion_score. We can call CollusionDetector’s process with a fabricated vote history where two experts align 100% and see if collusion_result comes back with is_suspicious = True. This ensures that collusion logic triggers appropriately (though collusion’s effect on decisions might just be reporting, unless it influences weights).
3. Property-based and invariant tests:
No state leakage invariant: Run two subsequent ticks of the system with different inputs and ensure that an expert’s output for instrument A at tick2 does not depend on instrument B’s data from tick1. Practically, this means resetting or re-instantiating experts between runs in tests, or checking that state dicts only contain keys they should. We can instrument the expert state: after one tick, mutate EURUSD data drastically and ensure XAUUSD next output remains consistent. This is a bit tricky to automate, but essentially we want to guarantee instrument_state keys don’t bleed (the code’s use of per-key deques and normalization already suggests it won’t). A test could explicitly inspect the internal instrument_state dict after a process call: confirm it has exactly entries for 'EURUSD' and 'XAUUSD' and no unexpected keys, and that those entries only changed in fields corresponding to data provided.
Output schema invariants: For any expert’s process output, verify it adheres to the contract: contains 'voting_proposal', 'confidence', etc., and that the types and ranges are correct. This can be done with hypothesis (property-based testing) by sending various random market_data inputs. The invariant we assert: the returned dict must always have 'voting_proposal' as a dict with an 'action' field (non-empty) and 'confidence' as a float between 0 and 1. Also, 'confidence' in the output dict should match the '<ExpertName>_confidence' key and the confidence inside the proposal if applicable. Essentially, ensure internal consistency: for example, the coordinator in its _normalize_vote_entry expects certain fields – we can assert those expectations on expert outputs upfront so that the coordinator never sees something unexpected.
Consensus vs. inputs: A property we expect: if all experts vote the same direction for an instrument, the committee decision for that instrument should be that direction (monotonicity of consensus). We can test random combinations of votes: generate random expert votes and compute aggregated decision via our aggregation function, and verify that the action chosen corresponds to the max weighted sum. If we include slight noise, we can verify that adding a neutral vote doesn’t flip a decided majority (neutral should either be ignored or at least not outweigh a directional vote). These tests validate the consensus algorithm’s correctness.
Performance and stress test: While not unit test per se, we should test the module’s performance with a high number of experts or instruments to ensure robustness. For instance, simulate 10 experts and 10 instruments with random votes and run coordinator aggregation to see it handles it within time and yields outputs of correct size (10 instruments decisions). This can flush out any quadratic slowdowns or memory issues.
4. Test environment and tools:
We will use dependency injection or monkeypatching to simulate the SmartInfoBus for unit tests to avoid needing the real InfoBus. For example, give experts a dummy bus object with a .get that returns from a dict, and .set that records to a dict, so we can inspect what they would publish without a running bus. This way, tests can run in isolation.
Use pytest and possibly hypothesis (for generating varied inputs). The code’s design (functional style for many calculations) lends itself to property tests.
We also plan integration tests possibly in an async context if needed (since process methods are async). We will run them either in an event loop or adapt them to synchronous for test by temporarily removing async (for pure computation that’s fine).
Logging can be captured in tests to assert that warnings/errors are emitted when expected (e.g., if we feed bad data, ensure a warning log contains "No valid price data" as expected).
By executing this test plan, we will gain confidence in each part of the system:
The low-level indicator math is correct.
Each expert’s decision logic triggers appropriately.
The coordinator correctly synthesizes those decisions.
The overall system handles edge cases (no data, conflicting inputs, etc.) gracefully as designed.
Moreover, these tests will act as a safety net for future refactoring. For example, after unifying action labels, we can re-run the tests to ensure nothing breaks (unit tests would catch if, say, an expert accidentally returned an unknown label; integration tests would catch if the coordinator no longer finds an expert’s vote due to a key naming issue). This aligns with the expectations of a senior quant developer: rigorous testing to validate that mission-critical code not only works in sunny-day scenarios but is robust to rainy-day scenarios too.
